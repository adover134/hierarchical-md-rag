## 데이터와 DB

| 용어 | 뜻 |
|---|---|
| RAG | 문서를 검색해 그 근거로 답을 만드는 방식 |
| LLM / Ollama | 답을 쓰는 언어 모델 / 그 모델을 내 컴퓨터에서 돌리는 도구 |
| kordoc | HWP를 Markdown으로 읽는 Node library. parser가 쓴다 |
| Gradio / FastAPI | 채팅 화면을 만드는 도구 / API 서버를 만드는 도구 |
| Kiwi | 한국어 형태소 분석기. 낱말을 뜯어 질문 키워드와 기관명 사전에 쓴다 |
| 어간 | 낱말의 변하지 않는 부분(예: "사업을" → "사업") |
| 공고문 | 나라장터에서 가져온 입찰공고 문서(HWP, HWPX, PDF) |
| parser | HWP/HWPX를 Markdown으로 바꾸는 도구(skill 또는 service). 이 저장소는 parser 저장소를 활용해 Markdown을 얻는다 |
| metadata CSV | 공고별 기관명, 사업명, 금액 등을 적은 `metadata.csv`(예전 표기 "공고 목록"). 이 저장소가 나라장터 엑셀로 만들고 빈칸을 채운다. 기관명 사전과 순위·금액 질문에 쓴다 |
| chunk | 문서를 최대 1,000자(200자 겹침)으로 자른 조각. 검색의 단위다 |
| 평탄화 | 표를 `라벨: 값` 줄로 풀어 쓰는 처리 |
| embedding | 글을 숫자 vector로 바꾼 것. 의미가 비슷하면 vector도 가깝다 |
| 밀집 검색 | embedding 거리로 비슷한 chunk를 찾는 검색 |
| BM25 | 낱말이 겹치는 정도로 찾는 검색. 저장은 하지만 지금은 검색에 쓰지 않는다 |
| ChromaDB | chunk와 embedding을 저장하는 DB(`data_index/`) |
| doc_id | parser Markdown 내용에서 만든 문서 식별자. 내용이 바뀌면 새 문서로 취급한다 |
| upsert | 같은 `doc_id`가 있으면 지우고 새로 넣는 방식 |

## 질의 처리

| 용어 | 뜻 |
|---|---|
| process | 질문을 받아 답을 만들기까지의 처리 전체(질문 분석, 검색, 답변) |
| 후보 pool | 재정렬 전에 일단 뽑아 둔 chunk 묶음. 요청 수의 15배(최소 150) |
| 기관 필터 | 질문에서 찾은 공고(`org` 값)의 chunk만 후보로 남기는 처리. `org`에는 공고명이 들어간다 |
| 재정렬 (hybrid 검색) | 후보를 밀집 0.6 + 낱말 겹침 0.4 점수로 다시 매기는 것 |
| top-K | 재정렬 뒤 답변 모델에 넘기는 chunk 수. API 기본 24, 평가 5 |
| main (평가표) | 평가표에서 "main"은 `two_stage` process를 가리킨다. branch 이름과 다르다 |
| `two_stage` | 근거를 먼저 정리한 뒤 답하는 방식(기본) |
| `multi_agent` | 질문을 1\~3단계로 쪼개 단계별로 값을 찾는 방식 |
| 단축 경로 | 문서 검색 없이 엑셀 정보로 바로 답하는 경로(순위, 금액 등) |

## 평가

| 용어 | 뜻 |
|---|---|
| 3×2 비교 / 칸 | process 3가지 × DB 2가지, 6칸. 한 조합이 한 칸이다 |
| 쌍체 비교 | 같은 질문의 두 조건 점수를 짝지어 비교하는 것 |
| 거부 답변 | "찾지 못했다"고 답한 것. 현재 채점은 점수 평균에 그대로 넣는다 |
| 순수 밀집 pool | 필터 없이 embedding만으로 뽑은 후보 |
| process가 만든 pool | process가 실제로 쓰는 방식(기관 필터 포함)으로 뽑은 후보 |
| chunk 누락 coverage | loader가 읽은 글이 chunk에 얼마나 남았는가 |
| 팀 process / 팀 DB | 팀 프로젝트(AI_7-team)의 처리와 DB. 비교 기준이다 |
| 현재 DB | 이 프로젝트의 parser와 chunking으로 만든 DB |
| subagent 채점 | API 키 없이 Claude subagent가 저장된 답을 채점하는 방식 |
| rubric v6 | 지금 쓰는 채점 기준. 팀 rubric(4개 축, 0\~5점)에 추가 기준 4개([채점 규칙](judge_rules.md)) |
| Correctness | 주된 값이 맞는가 |
| Answer coverage | 기대 답변의 핵심 정보가 빠짐없이 들어 있는가 |
| Faithfulness | 답이 검색된 근거에 기대는가 |
| Context relevance | 검색된 근거가 질문과 관련 있는가 |
| 주된 값 | Correctness에서 정답으로 보는 값. 괄호 안 부연(내역, 세부)은 제외한다 |
| 머리글 | chunk 앞에 붙는 `[공고명 - 문서 p.N] \| project=기관명` 줄. 답변 모델과 채점자가 함께 받는다 |
| Recall@N | 후보 N개 안에 정답 chunk가 들어 있는 비율. chunk를 보지 않고 만든 답은 chunk Recall에서 뺀다 |
| MRR | 정답이 몇 번째에 나왔는지의 역수 평균. 클수록 앞에 나온다 |
| p 검정 | 차이가 우연인지 p 값으로 판단하는 검정의 총칭. 이 프로젝트는 그중 부호 검정을 쓴다 |
| 부호 검정 | 같은 질문끼리 올라간/내려간 개수만 세어 우연인지 보는 p 검정 |
| p (p 값) | 두 조건이 사실은 같다고 가정할 때, 지금만큼 차이가 날 확률. 작을수록 우연이 아닐 가능성이 크고, 보통 0.05보다 작으면 우연이 아니라고 본다 |
