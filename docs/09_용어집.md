## 데이터와 DB

| 용어 | 뜻 |
|---|---|
| 공고문 | 나라장터에서 가져온 입찰공고 문서(HWP, HWPX, PDF) |
| 파서 | HWP/HWPX를 Markdown으로 바꾸는 도구(skill 또는 service). 이 저장소는 파서 저장소를 활용해 Markdown을 얻는다 |
| 공고 목록(엑셀) | 공고별 기관명, 사업명, 금액을 적은 표. 기관명 사전과 순위·금액 질문에 쓴다 |
| 청크 | 문서를 1,000자 안팎(200자 겹침)으로 자른 조각. 검색의 단위다 |
| 평탄화 | 표를 `라벨: 값` 줄로 풀어 쓰는 처리 |
| 임베딩 | 글을 숫자 벡터로 바꾼 것. 의미가 비슷하면 벡터도 가깝다 |
| 밀집 검색 | 임베딩 거리로 비슷한 청크를 찾는 검색 |
| BM25 | 낱말이 겹치는 정도로 찾는 검색. 저장은 하지만 지금은 검색에 쓰지 않는다 |
| ChromaDB | 청크와 임베딩을 저장하는 DB(`data_index/`) |
| doc_id | 파서 Markdown 내용에서 만든 문서 식별자. 내용이 바뀌면 새 문서로 취급한다 |
| upsert | 같은 `doc_id`가 있으면 지우고 새로 넣는 방식 |

## 질의 처리

| 용어 | 뜻 |
|---|---|
| 프로세스 | 질문을 받아 답을 만들기까지의 처리 전체(질문 분석, 검색, 답변) |
| 후보 풀 | 재정렬 전에 일단 뽑아 둔 청크 묶음. 요청 수의 15배(최소 150) |
| 기관 필터 | 질문에 나온 기관의 청크만 후보로 남기는 처리 |
| 재정렬 | 후보를 밀집 0.6 + 낱말 일치 0.4 점수로 다시 매기는 것 |
| top-K | 재정렬 뒤 답변 모델에 넘기는 청크 수. API 기본 24, 평가 5 |
| `two_stage` | 근거를 먼저 정리한 뒤 답하는 방식(기본) |
| `multi_agent` | 질문을 1~3단계로 쪼개 단계별로 값을 찾는 방식 |
| 단축 경로 | 문서 검색 없이 엑셀 정보로 바로 답하는 경로(순위, 금액 등) |

## 평가

| 용어 | 뜻 |
|---|---|
| 3×2 비교 | 프로세스 3가지 × DB 2가지, 6칸 |
| 팀 프로세스 / 팀 DB | 팀 프로젝트(AI_7-team)의 처리와 DB. 비교 기준이다 |
| 현재 DB | 이 프로젝트의 파서와 청킹으로 만든 DB |
| 서브에이전트 채점 | API 키 없이 Claude 서브에이전트가 저장된 답을 채점하는 방식 |
| 루브릭 v2 | 채점 기준. 4개 축, 0~5점([채점 규칙](judge_rules.md)) |
| Correctness | 주된 값이 맞는가 |
| Answer coverage | 주된 값이 빠짐없이 들어 있는가 |
| Faithfulness | 답이 검색된 근거에 기대는가. 거부 답변은 제외한다 |
| Context relevance | 검색된 근거가 질문과 관련 있는가 |
| 주된 값 | 정답으로 보는 값. 괄호 안 부연(내역, 세부)은 제외한다 |
| Recall@N | 후보 N개 안에 정답 청크가 들어 있는 비율 |
| MRR | 정답이 몇 번째에 나왔는지의 역수 평균. 클수록 앞에 나온다 |
| p 검정 | 차이가 우연인지 p 값으로 판단하는 검정의 총칭. 이 프로젝트는 그중 부호 검정을 쓴다 |
| 부호 검정 | 같은 질문끼리 올라간/내려간 개수만 세어 우연인지 보는 p 검정 |
| p (p 값) | 두 조건이 사실은 같다고 가정할 때, 지금만큼 차이가 날 확률. 작을수록 우연이 아닐 가능성이 크고, 보통 0.05보다 작으면 우연이 아니라고 본다 |
