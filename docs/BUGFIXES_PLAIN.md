# 답변 추출 계층 버그 — 쉬운 설명

`docs/BUGFIXES.md`(검색/org 해석 계층 수정 기록)와 계획 파일(`docs/`에는 없고
세션 plan 파일로만 존재)에 나오는 기술적 설명이 어려울 때 참고하는 풀어쓴 버전.
코드 줄번호나 함수명 대신 실제 예시 위주로 설명한다.

## 전체 그림

검색(어느 문서/어느 문단을 가져올지)은 이제 다 맞다. 문제는 그 다음 단계 —
가져온 문단에서 "진짜 답"을 뽑아내는 규칙 코드다. 이 코드는 "질문이 예산에 관한
거면 이 패턴으로, 기한에 관한 거면 저 패턴으로" 식으로 20가지 넘는 케이스를
정규식으로 나눠서 처리하는데, 그 나눔 순서와 패턴에 구멍이 있다.

## 버그 A: "몇 퍼센트"가 "몇 개" 처리기에 잘못 걸림

질문: "낙찰 기준은 몇 퍼센트 이상인가요?" (정답: 89.745%)

이 코드는 "몇"이라는 글자만 보고 "아, 이건 개수/수량을 묻는 질문이구나" 하고
[개수 전용 처리기]로 보낸다. 근데 그 [개수 전용 처리기]는 %(퍼센트) 기호를
다룰 줄 모른다. 못 찾으면 그냥 포기하고 끝내버리는데, 문제는 바로 옆에 %도
잘 처리하는 [숫자 전용 처리기]가 따로 있는데도 그쪽으로 안 넘어간다는 것 —
[개수 전용 처리기]가 먼저 가로채서 실패한 채로 끝내버리기 때문. 그래서 "7개"라는
엉뚱한 값이 나왔다.

**수정**: "몇"이 있어도 문장에 %나 "퍼센트"가 같이 있으면 [개수 전용 처리기]로
안 보내고 처음부터 [숫자 전용 처리기]로 보낸다. 한 줄짜리 조건 수정.

## 버그 B: 비교 답변이 "단답형 정리기"에 잘못 씹힘

질문: "A사업과 B사업 중 예산이 더 큰 건?" (정답: 비교 문장 전체)

이 코드는 정상적으로 "A 문서: ... / B 문서: ... / 공통: ... / 차이: ..." 형태의
4줄짜리 비교 답변을 잘 만든다. 근데 그 답변이 최종적으로 나가기 전에 [단답형
정리기]라는 후처리 단계를 하나 더 거치는데, 이 정리기는 "이 질문은 예산 얼마냐고
묻는 단답형이네" 하고 착각한다 (질문에 "비교"라는 단어가 안 들어있으면 이 정리기가
"비교 질문"이라는 걸 못 알아채는 별도의 허술한 판별기를 쓰기 때문). 그러면
정리기는 "답변 텍스트 안에서 백틱(`)으로 감싸진 첫 조각을 그냥 뽑아서 그게 답이다"라고
우겨버리는데, 4줄짜리 비교문 안의 backtick 조각을 아무 맥락 없이 뽑아오니
"사업비는 `사업비는 중심, B 문서는`입니다" 같은 파편이 나온다. (실은 이런 "무조건
뽑아서 강제로 줄이는" 단계가 한 곳이 아니라 세 곳이나 있다 — 다 같은 실수의 변주다.)

**수정**: 이미 "이 답변이 비교문 4줄 구조인지" 정확히 판별하는 헬퍼가 코드에
따로 있다(이건 신뢰할 만함, 이미 3군데서 검증되어 쓰이는 중). 이걸 저 3곳의
[단답형 정리기]들 앞에 "이미 비교문이면 건들지 마" 가드로 끼워넣는다. 새 정규식
없이, 이미 있는 판별기를 재사용.

## 구조적 방어선: "이상하면 규칙 코드 말고 LLM한테 다시 물어봐"

예산 질문(n2)과 공사기간 질문(n4)은 정확히 어디서 왜 깨지는지 명확히는 못
찾았다(2000줄짜리 함수라 더 파고드는 게 비효율적). 대신 이렇게 접근한다:

- 예산 질문인데 답에 "1,000,000원"처럼 콤마 찍힌 금액 모양이 없다 → 이상하다,
  못 믿는다
- 기간 질문인데 답에 "40일"처럼 숫자+기간단위가 없다 → 이상하다, 못 믿는다
- 이렇게 "모양이 이상하면" 규칙 코드가 만든 답을 그냥 최종 답으로 내보내지 않고,
  이미 만들어져 있는 LLM 생성 경로(문맥 읽고 실제로 답변 문장을 만드는 쪽)로 넘긴다.

지금은 규칙 코드가 뭘 내놓든 그게 이상해도 무조건 최종 답으로 확정해버리고 LLM은
아예 호출도 안 하는 구조다. "결과물이 답 모양이 아니면 LLM에게 다시 맡긴다"는
안전장치 하나만 추가하는 것.

## 기술적 세부사항은 어디에?

정확한 파일/줄번호, 코드 스니펫은 `docs/BUGFIXES.md`(6~9번 항목)에 있다 —
이 문서는 "무슨 일이 일어나고 있는지"를 빠르게 다시 떠올리기 위한 요약이고,
실제 구현 참조용은 아니다.

## 결과

버그 A, 버그 B, 구조적 방어선 전부 적용 완료. n1/n3/n4/n5는 완전히 정답이
되었고, n2도 값은 맞는데 사소한 라벨 잔여 흔적만 남았다. n8은 더 이상 틀린 값을
내놓지 않고 정직하게 "확인 안 됨"이라고 답한다(진짜 정답을 찾으려면 검색
후보 개수를 늘려야 하는 별개 문제가 남아있음). n6/n7은 답변 구조는 온전해졌지만
비교 답변에 들어가는 내용 자체(예산 대신 상투 문구를 뽑아옴)는 여전히 부실함 —
이건 오늘 고친 것과는 다른 층위의 문제로 남겨뒀다.
