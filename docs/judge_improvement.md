# 채점기 개선 기록 (rubric v2 \~ v6)

> **기록 문서다.** 여기의 점수와 측정값은 적힌 실행과 버전 시점의 값이고 현재 값이 아니다.</br>
    현재 점수와 비용은 [07 결과](07_결과.md)의 "현재 결과" 한 곳에만 있다.

채점은 1.1에서 이미 gpt-oss에서 Claude subagent로 바꿨다. 이 문서는 그 다음 문제, 곧 **같은 답변이 라운드마다 다르게 채점되는 문제**와 그것을 줄이려고 만든 rubric v2를 정리한다. 모든 수치는 Claude subagent(Opus)가 채점한 값이고 40문항 평가셋(`eval_dataset_new20`, `eval_dataset_new20_v2`)에서 나왔다.

## 1. 문제: 어떤 흔들림이 있었나

| 관찰 | 증거 |
|---|---|
| 같은 답변인데 Answer coverage가 라운드마다 달랐다 | 답변 문자열이 같은 26문항 쌍을 `round3`(`dbcmp6`)과 `round7`(`dbcmp8`)이 채점했을 때 Answer coverage가 10문항에서 달랐다(9개 하락). Correctness와 Faithfulness는 0문항 |
| 원인: 괄호 안 세부 내역을 감점할지 기준이 없었다 | 같은 답변 `기초금액은 50,000,000원입니다.`가 한 라운드에서는 5점(`주된 값을 빠짐없이 포함한다`), 다른 라운드에서는 4점(`괄호 안 추정가격과 부가가치세 내역이 빠졌다`)이었다(m5, m18, n10에서 확인) |
| 값은 맞는데 라벨이 달라 4점이 됐다 | `기초금액`을 묻는데 `사업비는 약 2.9억 원 (285,125,000원)입니다`로 답한 단축 답변 3개(n1, n9, n15)가 Correctness 4점이었다 |
| 규칙이 rubric이 아니라 지시문에만 있었다 | "주된 값(괄호 밖) 기준"은 제가 subagent에게 보낸 지시문에 한 줄로 넣었던 것이고 rubric(`rubric.md`)에는 없었다. Answer coverage에는 그 줄도 없었다 |

## 2. rubric v2의 규칙

`scripts/claude_judge.py`의 `INSTRUCTIONS_V2`. 기존 4개 축(0\~5점)과 JSON 형식은 그대로 두고, 애매했던 경우를 번호 규칙으로 명시했다. 채점자는 적용한 규칙 번호를 근거에 적는다.

1. **주된 값.** 기대 답변의 괄호 밖 값·사실이 주된 값이다. 괄호 안 내역(추정가격, 부가세, 동복·하복 금액, 구성 항목)은 부차 정보다. 괄호 밖에 값이 없을 때만 괄호 안 값을 쓴다.
2. **Correctness.** 주된 값만으로 판단한다. 모두 맞으면 부차 정보가 빠지거나 달라도 5점, 하나가 틀리거나 빠지면 최대 3점, 핵심 값이 틀리면 0\~2점.
3. **Answer coverage.** 주된 값이 모두 들어 있는가만 본다. 부차 정보 누락은 감점하지 않는다. 일부가 빠지면 빠진 비율대로 낮춘다.
4. **표기와 라벨.** 숫자 표기 차이(쉼표, `원`, 공백, `약 …억` 병기, `5천만 원`=`50,000,000원`)는 같은 값이다. 질문이 묻는 금액 이름(기초금액, 추정금액, 사업예산, 사업금액, 예산)과 답변이 쓴 이름(예: 사업비)이 달라도 값이 같으면 감점하지 않는다.
5. **비교 질문.** 주된 사실은 선택한 대상(과 있으면 그 값)이다.
6. **답변 거부.** `문서에서 확인되지 않습니다` 등(`hint.refusal`)은 Correctness·Answer coverage 0점이고, Faithfulness는 채점 대상이 아니므로 **해당 없음(N/A)**이다(점수 칸에 0, 근거를 `N/A(거부 답변)`으로 시작). 집계는 이 항목의 Faithfulness를 평균에서 뺀다. Context relevance는 context만 본다. (처음 v2는 Faithfulness 5점으로 정했다가 `round10`에서 답을 못 내는 시스템이 유리해지는 것을 보고 2026-11-03에 N/A로 바꿨다.)
7. **힌트.** 항목마다 script가 기대 답변에서 뽑은 주된 값 후보(`hint.primary_values`)와 그중 답변에 문자열로 없는 값(`hint.missing`)을 준다. 문자열 일치 힌트일 뿐이고 최종 판단은 채점자가 한다.

코드: `python scripts/claude_judge.py export --runs <run>:<system> ... --out-dir <dir> [--rubric v1|v2]`(기본 v2, v1은 이전 라운드 재현용). 출력 폴더에 `rubric_version.txt`가 남는다. 단위 테스트는 `tests/test_claude_judge.py`(힌트 계산, v2 규칙 문구, 힌트 포함 여부).

## 3. 검증 1: 같은 항목을 두 번 채점하면 같은 점수가 나오는가 (`round8`, `round9`)

같은 80개 답변(`dbcmp6`의 main × 현재 DB 40개 + `dbcmp8`의 main × 제목 블록 DB 40개)을 v2로, 섞는 순서만 달리해 독립적으로 두 번 채점했다. 80항목 모두 검증을 통과했다.

| 축 | 두 번의 완전 일치 | ±1 이내 | 평균 절대 차이 |
|---|---|---|---|
| Correctness | 80/80 (100%) | 80/80 | 0.000 |
| Answer coverage | 76/80 (95%) | 80/80 | 0.050 |
| Faithfulness | 76/80 (95%) | 80/80 | 0.050 |
| Context relevance | 63/80 (79%) | 80/80 | 0.212 |

**답변이 같은 26문항 쌍의 점수 차이** (같은 라운드 안에서 두 항목을 비교):

| 축 | v1 (`round3` 대 `round7`) | v2 `round8` | v2 `round9` |
|---|---|---|---|
| Correctness | 0/26 | 0/26 | 0/26 |
| Answer coverage | **10/26** | 1/26 | 0/26 |
| Faithfulness | 0/26 | 0/26 | 0/26 |
| Context relevance | 15/26 | 7/26 | 7/26 |

- Answer coverage의 불일치는 10/26에서 0\~1/26으로 줄었다. 규칙 3(부차 정보 누락 불감점)의 효과다.
- v2(`round8`)와 v1(기존 점수)의 완전 일치: Correctness 79/80, Answer coverage 64/80, Faithfulness 78/80, Context relevance 52/80.

## 4. 검증 2: 라벨과 거부 답변 규칙 (`round10`)

규칙 4(라벨)와 6(거부)은 위 80항목에 해당 사례가 없어서, 단축 답변과 거부 답변이 든 `dbcmp7`의 두 칸(multi × 팀 DB 40개, 팀 × 팀 DB 40개)을 v2로 채점해 v1과 비교했다. 처음 낸 subagent 8개 중 4개가 사용 한도(rate limit)로 멈췄고, 한도가 풀린 뒤 이어서 마쳤다. 80항목 모두 검증을 통과했다.

| 칸 / 축 | v1 평균 | v2 평균 | 완전 일치 | v2가 높음 / 낮음 |
|---|---|---|---|---|
| multi × 팀 DB, Correctness | 4.925 | 5.000 | 37/40 | 3 / 0 |
| multi × 팀 DB, Answer coverage | 4.750 | 5.000 | 30/40 | 10 / 0 |
| multi × 팀 DB, Faithfulness | 4.550 | 4.600 | 33/40 | 4 / 3 |
| multi × 팀 DB, Context relevance | 4.300 | 4.550 | 17/40 | 16 / 7 |
| 팀 × 팀 DB, Correctness | 2.775 | 2.800 | 39/40 | 1 / 0 |
| 팀 × 팀 DB, Answer coverage | 2.575 | 2.750 | 33/40 | 7 / 0 |
| 팀 × 팀 DB, Faithfulness | 3.450 | 3.775 | 36/40 | 4 / 0 |
| 팀 × 팀 DB, Context relevance | 3.900 | 3.875 | 27/40 | 6 / 7 |

- **규칙 4(라벨)가 의도대로 작동했다.** 4점이던 n1, n9, n15가 모두 5점이 됐다(multi × 팀 DB의 Correctness 3개가 높아진 것이 이들이다).
- **규칙 3이 작동했다.** 단축 답변의 Answer coverage가 4점에서 5점이 된 문항이 multi에서 7개(m3, m5, m11, n1, n6, n9, n15) 등 모두 괄호 안 내역 누락으로 감점되던 것이었다. 낮아진 Answer coverage는 없다.
- **규칙 6(거부)은 큰 차이를 만든다.** 팀 × 팀 DB의 거부 답변 2개(n16, n17)는 Faithfulness가 v1 1점에서 v2(Faithfulness 5점 규칙)로 5점이 됐고(Correctness는 0점 그대로), 팀 칸의 Faithfulness 평균이 3.450에서 3.775로 오른 대부분이 이것이었다. 답을 못 내는 시스템의 Faithfulness가 부풀려지는 부작용이라 규칙을 N/A로 바꿨다. 위 표의 v2 Faithfulness 평균(3.775)은 이 부작용이 든 값이고, 거부 답변을 뺀 평균은 `scripts/grid_report.py`가 계산한다.
- 변하지 않은 결론: 이 80항목을 v2로 다시 채점해도 multi 대 팀의 격차(팀 DB 4.925 대 2.775, v2로는 5.000 대 2.800)는 그대로다.

## 4.1 거부 답변은 어느 시스템에서 나오는가

`문서에서 확인되지 않습니다`, `근거 부족으로 …생략합니다` 같은 문구가 든 답변을 정규식으로 세었다(40문항 중, 팀의 비교 fallback 문구 포함).

| 실행 칸 | 거부 답변 문항 |
|---|---|
| 팀 process, 단축 끔 (`dbcmp6`) 팀 DB / 최신 DB | 6 (m2, m3, m8, m15, n16, n17) / 8 (+ m13, n13) |
| 팀 process, 단축 켬 (`dbcmp7`) 팀 DB / 최신 DB | 3 (m2, n16, n17) / 5 (+ m13, n13) |
| main (`dbcmp6`) 팀 DB / 최신 DB | 1 (n14) / 0 |
| multi-agent (`dbcmp6`, `dbcmp7`) | 0 |

거의 팀 process에서 나온다. main에서도 한 문항(n14, 팀 DB)에 있었고, 1.1 이전 main 실행(`dbcmp3`, `dbcmp4`)에서는 1\~3문항이 있었다.

## 5. 한계와 남은 일

한계
- 항목 80개 중 75개가 Correctness 5점이라 천장에 가깝다. 두 번의 채점이 100% 일치한 것에는 쉬운 항목이 많다는 영향이 있다.
- 이 검증은 **일관성**(같은 기준이 같은 점수를 내는가)만 본다. 점수가 사람이 보는 정답과 맞는지(타당성)는 사람 채점과 비교하지 않았다.
- 채점자는 모두 같은 모델 계열(Opus subagent)이다. 다른 모델과의 일치도는 재지 않았다.
- **Context relevance는 규칙을 추가하지 않았고 여전히 흔들린다**(두 번의 완전 일치 79%, 평균 절대 차이 0.212, v1 대비 `round10`에서 높음 16 대 낮음 7). 이 축은 검색된 chunk가 쌍마다 달라 일부는 실제 차이이지만, 기준 자체도 느슨하다.
- 지금까지 보고한 점수(`dbcmp3`\~`dbcmp8`의 대부분)는 v1이다. v2 점수와 직접 섞어 비교하지 않는다. 필요하면 해당 칸을 v2로 다시 채점한다(칸당 40건, subagent 4개).

남은 일(우선순위는 정해야 한다)
1. \~\~규칙 6 결정\~\~ 거부 답변의 Faithfulness는 N/A로 제외하고 표에 `거부 N건 제외`를 병기하는 것으로 정했다(2026-11-03, 0점 처리와 비교해 선택. 현재 규칙은 [`judge_rules.md`](judge_rules.md)). `claude_judge.is_refusal`이 거부 답변을 가려내 `hint.refusal`로 알리고, `grid_report.load_scores`가 그 항목의 Faithfulness를 `None`으로 두어 평균과 쌍체 비교에서 뺀다. `run_experiment.py evaluate`의 요약 평균에는 아직 적용하지 않았다.
2. \~\~Context relevance 규칙\~\~ 추가하지 않기로 했다(2026-11-03). 의사결정은 Correctness와 최종 상위 5개(@5)로 하고 Context relevance는 보조로만 읽기 때문이다. 이 축은 두 번의 채점 완전 일치가 79%로 가장 불안정하므로, 이 축의 차이만으로 결론을 내리지 않는다.
3. **보고된 칸 전체를 v2로 재채점**해 한 기준으로 맞춘다(`dbcmp6` 6칸, `dbcmp7` 4칸 중 이번에 2칸 완료, `dbcmp8` 1칸).
4. **채점기가 같은 DB로 직접 RAG를 수행해 자기가 찾은 정보와 생성 답변을 비교하는 방식**(제안). 기대 답변이 틀렸거나 표기가 다른 경우에 기준을 보강할 수 있다. 채점이 시스템과 같은 DB에 의존하게 되어 독립성이 약해질 수 있으므로, 기대 답변 대조를 주로 하고 DB 검색은 보조로 쓰는 설계가 필요하다. 당시에는 구현하지 않았다(2026-11-28에 DB 대신 원본 문서를 검색하는 방식으로 구현, 아래 "원본 검증").
5. 다른 모델 또는 사람 채점과의 일치도 확인(타당성 검증).

- **Answer coverage가 가장 많이 움직였다.** 규칙 3(괄호 안 내역 불감점)으로 단축 답변과 괄호 안 값이 빠진 답변이 5점이 됐다. multi(단축 켬) 두 칸은 4.750, 4.675에서 5.000이 됐다.

- **결론이 바뀐 것 하나:** `dbcmp6`의 팀 process에서 "최신 DB가 팀 DB보다 나쁘다"(Correctness -0.225, p=0.031)가 v2에서는 -0.150, p=0.625로 유의하지 않다. 이전에 유일하게 유의했던 DB 효과가 사라졌다. 이 차이는 채점 변동 안에 있었다는 뜻이다.
- **변하지 않은 결론:** process 효과(팀 대 main, multi)는 그대로 크고(+3.55\~+3.93, p<0.001), main과 multi는 Correctness로는 구분되지 않는다(+0.225 p=0.125, +0.100 p=0.5).
- **거부 판정 보정:** `round11` 채점자가 `is_refusal` 오판 한 건을 알려 줬다. main × 팀 DB의 n14는 정답(90일)을 낸 답변 끝에 `문서에서 확인되지 않습니다.` 한 줄이 덧붙은 경우인데 거부로 분류됐다. 실제 거부 답변은 모두 공백을 뺀 길이가 53자 이하여서 80자 상한을 두어 이 경우를 거부에서 뺐다(테스트 추가).

## 검색 지표 (2026-11-28)

code로 계산하는 지표의 변경이다. LLM 채점 기준과 점수는 바꾸지 않았다. 바꾸기 전과 후의 code를 보이고 승인받았다.

| 지표 | 전 | 후 |
|---|---|---|
| 문서 순위 지표 | MRR: 정답 문서가 모두 모이는 chunk 순위의 역수 | nDCG@N: 상위 N개 문서의 순위 가중 점수 |
| chunk Recall | chunk 번호만 맞춘 결과와 ID를 맞춘 결과 중 큰 값 | `chunk_id`(문서 ID와 chunk 번호) 전체가 같아야 인정 |

- nDCG@N은 정답 문서가 1개인 문항에서 2위 이하를 0으로 본다. MRR은 2위에 0.5를 줬다.
